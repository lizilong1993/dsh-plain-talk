# 0.1.11 效果实测

## 结论先说

1. 0.1.11 的改写方向没有被证据支持：同一模型下，0.1.11 在 4/4 个问题上中位字数都更长；但这个网关的采样噪声远大于版本差异，样本量不足以声称显著变差。
2. 我之前的说法有过头的地方：0.1.11 不是"新旧条款并列矛盾"，它只是把那三句替换了。真正的问题是替换后带数字的硬上限（12 行/300 字、列表最多 5 条）变成了"按需展开""按需保留"这类软约束。
3. 本次发布回退到 0.1.10 的规则正文，并补了离线自检 npm test，防止同类软化再被发布。

## 先量噪声（这一步之前漏了）

同一份规则、同一个问题，连跑 4 次，输出字数：

| 问题 | 0.1.10 四次采样 | 极差 |
| --- | --- | --- |
| Nginx 502/504 | 345 / 176 / 326 / 243 | 169 |
| git push non-fast-forward | 352 / 258 / 319 / 274 | 94 |
| WebAssembly 调研 | 50 / 364 / 385 / 382 | 335 |
| CPU 打满排查 | 478 / 508 / 410 / 496 | 98 |

同一版本内部极差最大 335 字，跨题最大 1402 字（WebAssembly 那题 0.1.11 采样为 741/962/862/2143）。tempterature=0 在这个网关上并不保证可复现。

## 版本对比（中位数）

| 问题 | 0.1.10 中位 | 0.1.11 中位 | 差值 |
| --- | --- | --- | --- |
| Nginx 502/504 | 285 | 361 | +76 |
| git push | 297 | 515 | +218 |
| WebAssembly | 373 | 912 | +539 |
| CPU 打满 | 487 | 677 | +190 |

4/4 同向偏长，平均 +256 字。噪声底（单版本内极差）达 1402 字，所以只能说"方向一致地变长"，不能据此宣称统计显著。

## 规则正文的实际差异

逐行对比 npm 0.1.10 与 0.1.11 的 dsh/rules.js，只有三行不同：

| 项 | 0.1.10 | 0.1.11 |
| --- | --- | --- |
| 结论 | 先给结论，再给必要细节 | 第一句直接回答最关心的事…直接给成品 |
| 长度 | 默认不超过 12 行、300 字 | 普通回复以 12 行、300 字以内为参考；需要完整步骤…按任务需要展开 |
| 列表 | 列表最多 5 条；只给一个下一步 | 用列表呈现并列项，按需保留完整条目…答完就停 |

后两行把唯一的数字上限换成软表述，这是可验证的规则退化，不依赖采样。

## 处理

- dsh/rules.js 回退到 0.1.10 正文（与 npm 0.1.10 逐字节一致，1596 字节）
- npm test：17 项离线断言，其中包含"长度上限与列表上限各只有一种说法且带数字"
- 新版发布此回退

## 怎么复现

```bash
npm test                                      # 离线契约检查，不需要模型
node test/noise.mjs                           # 采样噪声（约 32 次生成）
node test/bench.mjs --versions 0.1.10,0.1.11  # 版本对照
node test/determinism.mjs                     # 同输入多次调用是否一致
```

test/bench.mjs 直接从 npm 拉指定版本的规则正文，不依赖本地仓库状态。

## 遗留问题

噪声这么大，单靠这个本地网关做不了可靠的效果判定。要真正评估提示词改动，需要：固定随机种子或可复现的推理后端、每臂 20+ 采样、并用配对统计而不是均值比较。
